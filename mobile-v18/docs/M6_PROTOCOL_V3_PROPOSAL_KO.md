# M6 BLE 프로토콜 v3 제안 (미적용 · 호환성 계획)

V18은 PR #21의 **프로토콜 v2를 그대로** 사용합니다. 펌웨어와 `core/protocol.hpp`는 바꾸지 않았습니다. 이 문서는 V18 앱이 v2에서 부족하다고 확인한 점과, 바꿀 경우의 호환 계획입니다.

## v2에서 부족한 점 (V18 실측 기준)

| 앱 기능 | v2 지원 | V18의 현재 처리 |
|---|---|---|
| 알람 최대 8개 · 요일 반복 | `alarm_set {h,m,en}` 알람 1개, 매일 반복 | 24시간 안에 울릴 **다음 알람 1개만** 전송, 연결할 때마다 다시 맞춤. 없으면 `en:false` |
| 알람별 스누즈 시간 (0/5/10/15분) | 고정 5분 (`kSnoozeMin`) | 볼의 스누즈는 5분. 앱 화면/앱 알림만 알람별 시간 사용 |
| 조용한 알람 | 없음 (`sound` 전역 on/off만) | 앱에서만 진동·화면 알림 |
| 알람별 포켓몬 | 없음 (파트너 1종) | 앱 아침 화면에만 표시 |
| 포모도로 휴식 단계 | `focus_start {min}` 집중만 | 집중 단계만 볼과 동기화, 휴식은 앱 전용 |
| 확장 도감 16종 | `partner` 8종 | 8종 밖은 볼로 보내지 않고 안내 문구 표시 |

**위험:** 앱이 오래 연결되지 않으면 볼에 남은 알람이 주말에도 매일 울릴 수 있습니다. 앱 알람 화면에 이 제약을 표시했습니다.

## 제안: v3 (하위 호환)

```
{"v":3,"s":..,"q":..,"c":"alarm_slot","i":0..7,"h":0..23,"m":0..59,"d":<weekday bitmask 0..127>,"en":bool,"sz":0|5|10|15,"quiet":bool}
{"v":3,...,"c":"alarm_clear","i":0..7}
State v3 추가 필드: "al":[[i,en,h,m,d,ringing],...] (MTU 185 기준 8개면 초과 → "al_rev" 정수만 넣고 별도 "alarm_list" 읽기 특성 추가)
```

- 펌웨어는 `v:2` 명령을 지금처럼 처리하고, `v:3`을 추가로 받습니다. `alarm_set`(v2)은 슬롯 0의 매일 알람으로 매핑합니다.
- 앱은 연결 직후 상태의 `fw`(예: `m6-0.3.x`)나 `get_state` 응답으로 v3 지원 여부를 판단하고, 미지원이면 현재 v2 방식으로 동작합니다.
- 8개 알람 목록은 상태 알림(200 B)에 넣지 않습니다. MTU 185에서 알림 크기 초과를 피하기 위해 읽기 전용 특성 `edc00005-…`(alarm list)를 추가하는 안을 권합니다.
- NVS 스키마: 슬롯 8개 × 6바이트. 기존 단일 알람은 부팅 시 슬롯 0으로 마이그레이션.

## 검증 계획

1. `tests/protocol_test.cpp`에 v2/v3 혼합 시퀀스 추가 (v2 앱 + v3 펌웨어, v3 앱 + v2 펌웨어 `ver` NACK → v2 폴백).
2. `ble_bridge_host.cpp` 브리지로 V18 `ble_bridge_app_test.mjs` 확장.
3. G3 실기기: 요일 알람이 자정을 넘을 때, 정전(RTC 셀 없음) 뒤 앱 재연결 시 중복/누락이 없는지.

이 제안은 하드웨어 게이트(G1–G5)와 PR #21 리뷰 이후 결정할 사항입니다.
